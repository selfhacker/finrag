# 会话洞见归档技能

## 定位

本项目有一套"面试答辩归档体系"（`docs/思考与方案/`），把开发过程中主动追问的
"如果规模大了会怎样 / 为什么这么做而不是那样做"沉淀成结构化条目，作为面试前
的直接弹药库。本技能把"会话 → 归档"这个动作标准化，防止历史病灶复发：

1. **问答错位**——标题问 A、首句答 B（原始对话是多连问，归档时只留一半，残句悬空）；
2. **追加不同步**——文件头主题范围、关联知识链、README 索引漏更新；
3. **行号腐烂**——引用 `file.py:NN`，代码一改就悬空。

归档来源可以是**当前会话**，也可以是**用户粘贴/指定的其他会话内容**（跨会话时
只依据用户提供的文本提取，不凭空补全上下文）。

## 归档流程（五步）

### 1. 判定是否值得归档

满足任一即归：

- 追问过"这样写在生产环境行吗"或"为什么这么做而不是那样做"；
- 有量化数据支撑的结论（账本、实测分数、耗时对比）；
- 概念辨析（X vs Y）且能落到本项目的选型判据；
- 踩坑实录（报错原文 + 排查路径 + 修复 + 根因）。

纯操作步骤、一次性调试过程、与项目无关联的闲聊**不归**。

### 2. 提取五要素

从会话内容中提取（缺失的标注"待补"，**不得编造**）：

| 要素 | 说明 |
|---|---|
| 问题现场 | 谁在什么语境下问了什么 / 撞了什么报错 |
| 结论先行 | 一句话说清答案（读者只看这句也能带走核心） |
| 量化依据 | 数字表、实验结果；没有就写定性论证 |
| 决策记录 | 选了什么、为什么现在不升级、回头改的触发条件 |
| 面试话术 | 30 秒可复述的版本 |

### 3. 选定主题文件

按内容归属选既有文件：`RAG与检索.md` / `Agent架构.md` / `评估体系.md` / `学习路径.md`；
都不合适时**新建主题文件**（命名 `<主题>.md`，文件头写"主题范围 + 对应实现"，
并在 `docs/思考与方案/README.md` 索引加行）。

编号续接该文件当前最大 Q 编号 +1，不重排不插号。

### 4. 按统一写作模板写条目

```markdown
## Qn · 标题（问句或论断）

<首段必须直接回答标题——禁止"有，且是…"式答非所问的开头>

<正文：问题现场 → 结论 → 量化/论证 → 决策记录 → 面试话术>

关联 → <相关条目，只引用不复制正文>
```

语言与风格：简体中文，延续 Java 工程师类比的教学风格；术语首次出现给出英文原文；
口语洞察可保留（如"算得少而不是算得快"），语病不留。

### 5. 同步点检查（每次归档必做，缺一即补）

- [ ] 文件头"主题范围"是否涵盖新条目主题
- [ ] 文件尾"关联知识链"是否追加新环节
- [ ] `docs/思考与方案/README.md` 索引的主题描述是否需要更新
- [ ] 新条目与既有条目的双向"关联 →"（新条目指向旧条目，强相关的旧条目回指）
- [ ] **行号引用：禁止 `file.py:NN` 形式**（代码演进必漂移），一律用"函数名 + 行为"定位
- [ ] 若条目描述了代码行为，须与当前实现核实一致（不凭印象写"代码里是这么写的"）

## 质量红线

- 不得编造未在会话中出现的数据与结论；引用实验结果必须是真实跑过的；
- 归档 ≠ 复制对话：重写为"面向三个月后的自己"的完整叙述，不依赖对话上下文也能读懂；
- 一条只讲一个问题，衍生话题拆新条目并用"关联 →"连接；
- 涉及"README 第 X 节 / AGENTS.md 某条"的引用，落笔前核对该节存在且内容相符。
