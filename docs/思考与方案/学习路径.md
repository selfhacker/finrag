# 学习路径 — finrag vs pi agent

> 背景：在深入打磨 finrag 时产生的方向性问题——是继续深耕本项目，还是去学 pi agent，还是都学。
> 结论先行：**主次分明的"都学"——finrag 是动手的主作品，pi 只做源码阅读材料**。

---

## pi agent 是什么

[earendil-works/pi](https://github.com/earendil-works/pi)（badlogic/pi-mono）：一个"反框架"哲学的 agent 工具包——*lean, hackable, no bloat*：

| 包 | 职责 |
|---|---|
| `pi-ai` | 统一多 Provider LLM API（OpenAI/Anthropic/Google/Ollama…），provider 中立的消息格式 |
| `pi-agent-core` | 手写 agent loop + 工具执行 + 会话状态管理（核心 loop 仅约 150 行） |
| `pi-coding-agent` | 极简 coding agent CLI（TUI、会话树、扩展系统、技能系统） |

另有 PyPI 上的 Python 版 `pi-coding-agent`（致敬之作，同为学习型项目）。

## 定位对比

| | **finrag（本项目）** | **pi agent** |
|---|---|---|
| 领域 | RAG + Tool Calling 问答 | Coding agent（读写代码、跑命令） |
| 核心技术 | 检索链路：分块/embedding/Dense+BM25/RRF/重排 | Agent 本体：loop、turn 管理、会话持久化、上下文压缩 |
| 框架观 | 用 LangGraph 图抽象编排 | 反框架，裸手写一切 |
| 已覆盖 | ✅ 混合检索、ReAct 图、异步并发 | ❌ 基本未涉及 |

## 为什么"读 pi"性价比极高：恰好补上 finrag 缺的三块（2026 面试高频考点）

1. **Context engineering / compaction**——pi 用摘要压缩替换旧消息防上下文溢出；finrag 只有内存态 MemorySaver，没有长对话管理 → 现成的演进方向。
2. **Provider 中立消息格式**——一份 transcript 在 Claude/GPT/Ollama 间无缝切换；对照 finrag 绑死 OpenAI 兼容接口的迁移性短板。
3. **裸写 loop vs 框架图**——150 行 loop 就是 `agent⇄tools` 回环去掉 LangGraph 的样子。读完才真正理解框架替你做了什么、值不值——workflow vs agent 辨析的终极素材（见 [Agent架构.md](Agent架构.md) Q1）。

## 执行计划

```
本周内:  继续收尾 finrag 打磨（noqa 体系已完成；待定项 pydantic-settings、functools.cache）
之后:   花 1-2 个晚上只读 pi 三样东西:
         - packages/agent/src/agent-loop.ts   （loop 本体）
         - compaction 逻辑                     （上下文压缩）
         - SessionRepo                         （会话持久化）
产出:   把洞察写进本目录归档（如"finrag 多轮记忆为什么是内存态，
        生产该怎么持久化和压缩？"→ 又一条工程化条目）
```

**明确不做的事**：不照着 pi 再写一个完整 agent 项目——和 finrag 重复劳动，边际收益低。"读它 + 把差距变成 finrag 的演进路线"才是复利。

## finrag 演进路线（Phase 1–4）

| 阶段 | 内容 | 状态 |
|---|---|---|
| Phase 1 | 评估闭环：golden set 双口径 + Hit@k/MRR + 三路检索对比 | ✅ 已完成（复盘见 [评估体系.md](评估体系.md) Q0） |
| Phase 2 | 可靠性：ReAct 循环 max_iterations 上限、上下文长度裁剪、显式退避重试 | 待做 |
| Phase 3 | 生产化：FastAPI 封装 + SSE 流式、SQLite checkpoint（替换内存态 MemorySaver）、结构化 JSON 日志 | 待做 |
| Phase 4 | 测试固化：pytest 覆盖 RRF 融合、重排降级、工具参数校验降级 | 待做 |

检索增强实验（Multi-Query / 父子分块 / CRAG / BGE-Reranker）不单列阶段，按性价比顺序融入日常迭代，清单与验证原则见 [RAG与检索.md](RAG与检索.md) 的"演进路线"。

Phase 2 的 max_iterations 与 Phase 3 的 SQLite checkpoint 正是上表"读 pi"两项洞察（loop 上限管理、会话持久化）的落地承接。
