# 评估体系 — 问题归档

> 主题范围：L1 检索评估落地（golden set 双口径、三路对比）、评估难度分层、
> LLM-as-Judge 忠实度原理、结构化输出兼容性踩坑。
> 对应实现：`eval/golden_set.yaml`、`eval/metrics.py`（L1 检索指标）、
> `eval/compare.py`（三路对比）、`eval/faithfulness.py`（L2 生成忠实度）。
> 归档时间：2026-09。
> 结构：两个主题分组（L1 检索评估 / L2 生成评估）。

---

## 一、检索评估（L1）

### Q0 · L1 检索评估是怎么落地的？（双口径 golden set + 三路对比）

**问题现场**：改分块大小、换检索策略之后，说不清"变好还是变坏"——没有考卷，优化全凭感觉。坊间文章都在喊"要能优化"，没人告诉你**优化的依据从哪来**。

**方案**：golden set（35 条人工标注）+ 双口径命中判定 + 三路检索对比实验。

- golden set 每条 = `query + expected_sources + answer + type`；
  type 分 direct（关键词直接命中）/ semantic（依赖语义理解）/ fuzzy（易混淆表述）三档难度；
- **双口径**（`metrics.py`）：
  - **文档级** `hit@k / mrr@k`——Top-k 是否命中期望来源文档，回答"能否把答案所在的文档召回"；
  - **答案级** `ans_hit@k / ans_mrr@k`——期望答案片段是否真实出现在召回 chunk 文本中，
    回答"喂给 LLM 的上下文里答案是否真的出现"，**更严格**。匹配经 `_norm()` 去空白归一化；
- 三路对比（`compare.py`，支持 `--skip-rerank` 秒级回归）。

**为什么必须双口径（假阳性视角）**：文档级只要目标文档出现在 Top-k 就算命中——哪怕召回的是同文档的无关 chunk，"表面 ✓ 实际 ✗"，LLM 拿到的上下文里没答案照样编造。答案级专门抓这种假阳性。用混淆矩阵的语言：文档级命中是"文档被召回"的真阳性，却可能是"答案进入上下文"的假阳性（术语速查 → [docs/概念与术语.md](../概念与术语.md)）。

**实测数据**（35 条，Top-5）：

| 策略 | 文档Hit@1 | 文档Hit@3 | 文档MRR@5 | 答案Hit@1 | 答案Hit@3 | 答案MRR@5 |
|---|---|---|---|---|---|---|
| dense（纯向量） | 91.4% | 100% | 0.952 | 88.6% | 100% | 0.933 |
| **hybrid（Dense+BM25+RRF）** | **94.3%** | 100% | **0.971** | **91.4%** | 100% | **0.957** |
| hybrid + LLM 重排 | 88.6% | 97.1% | 0.936 | 88.6% | 94.3% | 0.918 |

**三条结论**：
1. **hybrid > dense**（约 +3pp，两口径一致）：BM25 关键词召回补语义漏网；
2. **答案级 < 文档级约 3pp**：存在"文档召回对、含答案 chunk 未进 Top-3"的假阳性，答案级更贴近真实生成质量；
3. **LLM 重排负优化**（量化复盘见 [RAG与检索.md](RAG与检索.md) Q8）→ 工程决策：小语料默认关重排（`ENABLE_RE_RANK=false`），语料扩大后复测回正再开。

**实施踩坑（四坑 + 一次完整闭环）**：

| 坑 | 现象 | 修复 |
|---|---|---|
| 相似度越界警告刷屏 | DashScope embedding 出现负相似度，langchain 的 UserWarning 把整包候选打出来 | `similarity_search_with_score`（按距离升序）；RRF 只依赖排名，不受影响 |
| 分组明细错位 | 按 type 分组的 Hit@3 数字明显不对 | 全量结果列表与过滤子集直接 zip 导致错位 → 按原索引收集对应结果 |
| 串行评估慢 | rerank 每条串行调 LLM，10 分钟跑不完 | `asyncio.gather` 并发 + `Semaphore(4)` 限流，压到约 5 分钟 |
| 「审计委员会」假阳性 | 答案明明在文档里，答案级却报未命中 | 分块断行把句子切成 `每季度至少召开\n一次会议`，严格子串失配 → `_norm()` 归一化空白后命中。完整走了一遍「评估发现问题 → 定位 → 修复 → 复测」闭环 |

**使用原则**：每次优化前后各跑 `eval/compare.py --skip-rerank`（秒级、零 LLM 调用），指标回正或上升才合入——让每个工程决策都有数字背书。

**面试话术**："我有 35 条 golden set 双口径评估：文档级抓'找没找到文档'，答案级抓'上下文里到底有没有答案'。实测 hybrid 比纯向量的 Hit@1 高 3 个点；还用数据证明了 LLM 重排在小语料是负优化（答案 Hit@3 从 100% 掉到 94.3%），于是默认关闭。评估还抓过一个假阳性——分块断行导致答案子串失配，归一化空白后消除，完整走了'发现问题→定位→修复→复测'的闭环。"

关联 → [RAG与检索.md](RAG与检索.md) Q8（重排为什么负优化）、下方 Q1（评估难度分层）

## 二、生成评估（L2）：忠实度 faithfulness

### Q1 · 实现 AI 评估是不是难度很大？

**问题现场**：已有 L1 检索评估（golden set + Hit@k/MRR@k），被问"AI 评估是不是很难"，想到 RAGAS/TruLens 那一堆框架就望而生畏。

**结论先行：难的不是写代码，是定义 ground truth。** 按层级拆开看难度分布：

| 层级 | 评什么 | 难度 | 本项目现状 |
|---|---|---|---|
| L1 检索评估 | 召回对不对 | ★ 低——本质是字符串匹配+排名倒数，`metrics.py` 仅 114 行 | 已有（35 条 golden set，双口径） |
| L2 生成评估 | 答得对不对、有没有胡编 | ★★ 中——无唯一正确答案，只能模糊判定 | faithfulness.py（原子断言级忠实度） |
| L3 Agent 评估 | 工具选对没、会不会死循环 | ★★★ 高——轨迹标注成本高 | 未做（先记轨迹不评分） |

**为什么大家觉得难**：① 生成无唯一答案；② LLM-as-Judge 本身会漂（换 judge 分数就变）；③ Agent 轨迹（调了几个工具、几轮退出）比单点答案难标注。

**工程姿势**：别一上来就搬 RAGAS 全家桶——先 L1 确定性指标立门禁 → 失败 case 人工看 → 真要量化生成才上 Judge。`eval.sh --skip-rerank` 秒级不花钱，才是日常回归该有的样子。

**面试话术**："评估难不在写指标，难在定义 ground truth。检索层我用 golden set + Hit@k/MRR@k，确定性可回归；生成层用 LLM-as-Judge 但只评 faithfulness——答案是否被上下文支撑，不评'好不好听'；Agent 层先记轨迹再谈打分。"

关联 → Q2（为什么单挑 faithfulness）

---

### Q2 · LLM-as-Judge 为什么只评 faithfulness（忠实度）？

**问题现场**：生成答案没有标准答案，人工标注贵 → 用另一个 LLM 当裁判（LLM-as-Judge）。但"评什么"是关键决策。

**faithfulness 定义**：把答案拆成**原子断言**（一句话只表达一个事实），逐条核查"能否从召回上下文推出来"，score = 被支撑断言数 / 总数。

**实证**（eval/faithfulness.py 内置 demo，judge 判词为真实输出）：

| 样例 | 答案特征 | 拆解结果 | 分数 |
|---|---|---|---|
| A 忠实 | 两句均出自上下文 | 2✓ 0✗ | **1.00** |
| B 半幻觉 | 前半有出处，后加"经营良好""预计破20亿" | 2✓ 2✗（逐条被抓） | **0.50** |
| C 全编造 | 数值全部漂移（12.5亿→30亿） | 0✓ 3✗ | **0.00** |

**核心洞察：主观评分会掩盖幻觉。** 样例 B 句子通顺、信息量大，"综合打 1-10 分"很可能给 8 分——写得越顺、编得越像真的，主观分越高。而断言核查是事实核查，接近客观判定（换个 judge 结论基本一致），能当回归门禁。

**Judge 两条铁律**（写进系统提示词）：
1. 只准依据上下文判定，严禁用自己的知识补证——否则"编得合理"会被误判 supported；
2. 数字/日期精确匹配——幻觉最常见形态就是数值漂移。

**可行动性**：faithfulness 低 → 上下文里没答案 → 回去修检索（正好接 L1 指标）；"综合分 7 分"什么都告诉不了你。

**面试话术**："我把答案拆成原子断言逐条核查上下文支撑，这是能当回归门禁的确定性判定——类比单元测试 assert；'答得好不好'类比代码评审打星，主观且不稳定，只做抽样人工看，不进指标体系。"

关联 → Q3（实现时的三个真坑）

### Q3 · faithfulness 实现踩坑实录（三个 400/静默失效）

**问题现场**：`eval/faithfulness.py` 首跑，三个样例全部 400。降级兜底如期工作（score=-1 不炸脚本），但 judge 全挂。逐个排查出三个坑——每一个都是"OpenAI 官方行为 ≠ OpenAI 兼容厂商行为"的活教材。

#### 坑 1：DeepSeek 不支持 `response_format(json_schema)`

```
400 - {'error': {'message': 'This response_format type is unavailable now', ...}}
```

新版 langchain-openai 的 `with_structured_output(Model)` **默认走 OpenAI 专有的 json_schema 模式**（`chat.completions.parse` 端点）。DeepSeek 兼容接口不支持。

**修**：`method="function_calling"`——用 tools 参数承载 JSON Schema，DeepSeek 的 tool calling 本项目 ReAct 已验证可用，同一条能力复用。

#### 坑 2：思考模型不支持强制 `tool_choice`

```
400 - {'error': {'message': 'Thinking mode does not support this tool_choice', ...}}
```

`.env` 的 `LLM_MODEL=deepseek-v4-flash` 是**思考模式模型**。`with_structured_output` 的 function_calling 方式会设置 `tool_choice` 强制调用指定函数，思考模式直接拒绝。

**修**：判官模型与业务模型解耦——`config.py` 新增 `LLM_JUDGE_MODEL`（默认 `deepseek-chat` 非思考版）+ `get_judge_llm()` 工厂。这正好印证裁判选型三原则：**便宜、快、确定性**——思考模型的思维链对判官无用，反增成本与延迟。

（旁注：主链路 ReAct 不受影响——`bind_tools` 不强制 tool_choice，模型自主决定是否调用。）

#### 坑 3：`model_copy(update={"model": ...})` 静默失效

最初想从 `get_llm()` 派生判官：`get_llm().model_copy(update={"model": LLM_JUDGE_MODEL})`。实测 `model_name` **纹丝不动**——langchain-openai 的 `model` 字段带 alias（`model_name`），pydantic v2 的 `model_copy(update=...)` 按内部键名写入，alias 键不命中，且**不报错**。

**修**：放弃魔法 copy，独立构造 `get_judge_llm()`（与 `get_llm`/`get_embeddings` 工厂同级，符合 config.py 配置中心定位）。教训：**对带 alias 的 pydantic 字段，copy-update 是静默陷阱，缺什么字段就老老实实显式构造。**

#### 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 结构化输出方式 | `method="function_calling"` | DeepSeek 兼容性（坑1） |
| 判官模型 | 独立配置 `LLM_JUDGE_MODEL` | 便宜快确定 + 解耦业务模型（坑2） |
| judge 失败处理 | score=-1 降级不抛异常 | 与工具铁律同款：评估器故障不炸脚本 |
| 输出契约 | pydantic `FaithfulnessAudit` | 与 tools.py 的 args_schema 一脉相承 |

**面试话术**："结构化输出我踩过两层兼容性坑：OpenAI 的 json_schema 模式 DeepSeek 不支持，要退到 function_calling；思考模型又不支持强制 tool_choice，所以判官模型独立配置走非思考版。这两层正好说明'OpenAI 兼容'只在接口签名层面成立，能力矩阵要逐项验证。"
