## 一、BM25 与打分机制

### Q1 · BM25 `get_scores()` 返回全量分数数组 —— chunk 多了，内存会不会爆？

#### 问题现场

`rag_retriever.py` 的 `retrieve()` 内 BM25 路打分处：

```python
bm25_scores = self._bm25.get_scores(_tokenize(query))
# 返回长度 = 语料库 chunk 总数 N 的 float 数组，scores[i] 是第 i 个 chunk 的得分
top_idx = sorted(range(len(bm25_scores)),
                 key=lambda i: bm25_scores[i], reverse=True)[:candidate_k]
```

第一眼的不适感：**不管查什么，都要给全部 N 个 chunk 打一遍分**。这在生产环境像"无索引全表扫描"。

#### 第一步：拒绝直觉，先算账

工程师的第一反应不该是"完了要优化"，而是**量化**——这块内存到底多大？

Python 的 float 是对象（约 24 字节对象头）+ 列表指针 8 字节，单元素实际成本 ≈ 32 字节（对比 Java 的 `double[]` 是紧凑的纯 8 字节/元素，这就是为什么 Java 里这种写法更无所谓）：

| chunk 数 | scores 数组内存 | 体感 |
|---|---|---|
| 几百（本项目现状） | ~几 KB | 忽略不计 |
| 1 万 | ~0.3 MB | 无感 |
| 10 万 | ~3 MB | 无感 |
| 100 万 | ~30 MB | 有感但可接受 |
| 1000 万 | ~300 MB | 该换方案了 |

**结论一**：这是 O(N) 个标量的物化，等价于 Java 里"查询结果只物化一列 `double[]`"，不是把整张表拉进堆。百万级才 30MB——**内存从来不是这里的真瓶颈**。如果没算这笔账就动手优化，就是在解决不存在的问题。

#### 第二步：找到真瓶颈 —— CPU，不是内存

真正随规模恶化的是三笔 CPU 开销：

1. **全量打分本身**：`get_scores` 复杂度 `O(N × query词数)`，每个 chunk 都要遍历 query 的每个 token 查倒排表；
2. **实现质量**：`rank_bm25` 是纯 Python 实现，无 C/Rust 加速，常数因子大；
3. **后续排序**：`sorted(range(N))` 是 `O(N log N)` 全量排序，而只要 top-k——可用 `heapq.nlargest(candidate_k, ...)` 降为 `O(N log k)`。

百万 chunk 时，单次查询是**秒级延迟**，此时 30MB 内存反而是小事。**能分清"内存瓶颈还是 CPU 瓶颈"本身就是一个面试区分点。**

#### 第三步：规模上去之后的演进路径

| 量级 | 方案 | 核心思想 |
|---|---|---|
| < 10 万 chunk | `rank_bm25` 内存内即可 | 当前选择 |
| 10 万 ~ 百万 | 进程内引擎：`tantivy-py`（Rust）/ SQLite FTS5 | 换 C 级实现 + 真·倒排索引 |
| 百万以上 | Elasticsearch / OpenSearch / Lucene | **WAND 等 top-k 剪枝算法**：利用倒排表按 IDF 从高到低累加，一旦剩余词项的理论最大分追不上当前第 k 名，提前终止——根本不给大多数 chunk 打完整分 |
| 任意大规模 | 两级架构：BM25 粗筛 top-1000 → 精排（reranker） | 工业界搜索/推荐标准形态，粗排保召回、精排保精度 |

关键洞察：**成熟引擎快，不是因为算得快，而是因为算得少**（剪枝/提前终止）。demo 代码和 Lucene 的差距是算法层面的，不是语言层面的。

#### 第四步：那本项目为什么还这么写？（决策记录）

1. **量级匹配（YAGNI）**：教学语料几百个 chunk，`rank_bm25` 毫秒级响应，为不存在的流量引入 ES 集群是负优化；
2. **教学价值优先**：`rank_bm25` 十行可见的实现让 RRF 融合逻辑完全透明，换成 ES 后融合黑盒化；
3. **复杂度是有价格的**：引入外部搜索引擎 = 部署 + 运维 + 数据同步链路。

**边界写在纸上**：触发条件 = 语料超过 ~10 万 chunk 或单查询 P99 超 100ms，届时按上表第一级替换 `tantivy-py`，接口不变。

#### 面试表达

> "我的混合检索里 BM25 这一路是全量打分，我当时专门评估过它的扩展性：内存上只是 O(N) 个 float，百万 chunk 也才 30MB，不是瓶颈；真瓶颈是 O(N×q) 的 CPU 打分加上纯 Python 实现。所以我在文档里写了明确的触发条件——语料到十万级就换 tantivy 或 Lucene 系引擎，靠 WAND 剪枝做到'少算'而不是'算快'。当前量级我刻意保持 rank_bm25，零部署成本且融合逻辑透明。"

### Q2 · `get_scores()` 这一行得到的是"排名"吗？

**不是——这一步只得到原始分数数组，排名由下一行 `sorted()` 才产生**（两步合起来才是完整的 top-k 检索）：

```python
# 第 1 步：打分（get_scores）—— float 数组，顺序与建索引时文档顺序一一对应
# 未命中任何 query 词项的 chunk 得 0.0；例: [0.0, 12.7, 0.0, 8.3, ...]
bm25_scores = self._bm25.get_scores(_tokenize(query))

# 第 2 步：排序 —— 这才产生"排名"
top_idx = sorted(range(len(bm25_scores)),
                 key=lambda i: bm25_scores[i], reverse=True)[:candidate_k]
```

Java 类比：`get_scores` ≈ 全量各算一遍分得 `double[]`；`sorted(range(N))` ≈ `IntStream.range(0,n).boxed().sorted(comparing(scores::get).reversed()).limit(k)`。

数组下标即身份：BM25 索引和 `_bm25_docs` 列表是**同序平行数组**，融合循环里用 `idx` 就能直接换回 chunk 文本（`self._bm25_docs[idx]`）。

### Q3 · BM25 打分模型的三个设计点（含项目自定义中文切分）

公式（TF-IDF 进阶版，Lucene/ES 的默认算法）：

```
score(D, Q) = Σ IDF(qᵢ) · f(qᵢ,D)·(k1+1) / ( f(qᵢ,D) + k1·(1-b+b·|D|/avgdl) )
```

1. **词频饱和**：分母里的 `k1` 让出现 100 次的词不再线性刷分；
2. **长度归一化**：`b·|D|/avgdl` 按文档长度打折，长短文档公平比较；
3. **IDF 稀有词加权**："华信科技"权重高，"的/了"权重低。

**项目自定义**（`_tokenize_cjk`）：中文没有空格无法直接切词，采用**双字(bigram)+单字混合切分**——"营业收入" → [营业, 业收, 收入] + [营, 业, 收, 入]。双字保匹配能力，单字防止过于稀疏。这是"中文检索为什么不能直接套英文方案"的现成例子。

## 二、多路召回与融合

### Q4 · 多路召回是什么？为什么两条路比一条强

多路召回 = **多种检索方式并行召回候选，再合并**，目的是弥补单一检索方式的盲区。

本项目两条路（`retrieve()` 内先后执行）：

| 检索路 | 原理 | 擅长 | 盲区 |
|---|---|---|---|
| **Dense（向量）** | Embedding 语义相似度 | 同义改写："市盈率"↔"P/E ratio" | 精确关键词/数字易偏 |
| **BM25（稀疏）** | 词频统计打分 | 精确术语、数字、专有名词 | 同义词字面不同找不到 |

典型互补例：
- 查询"市盈率"，文档写"P/E ratio" → BM25 匹配不到，Dense 靠语义捞回
- 查询"PE 12.5" 数字精确匹配 → Dense 可能捞偏，BM25 精确定位

概念区分（易混）：**多路召回求"捞全"（recall），重排求"捞准"（precision）**——先保证答案在候选池里，再精排把池子缩小。

---

### Q5 · RRF 公式里的 Σ 与 k=60

`score(chunk) = Σ 1/(k + rank_i)` —— Σ 就是累加：**对同一个文档，把它在每一路的排名倒数分累加**。

```
文档《华信科技年报》：Dense 排第 1，BM25 排第 3，k=60
总分 = 1/(60+1) + 1/(60+3) ≈ 0.0164 + 0.0159 ≈ 0.0323
```

对应代码就是 Dense 路与 BM25 路两个融合循环里的 `fused[key].score += 1.0 / (k + rank + 1)`，每个文档一个"积分账户"按名次攒分，最后按余额排序。

**为什么用排名倒数而不是原始分相加**：Dense 相似度（0~1）和 BM25 分（可 20+）量纲不同没法直接加；"排名"是两路天然统一的尺度 → 又一次归一化思想（见 Q6）。`k=60` 是平滑系数：让第 1 名和第 2 名差距不至于悬殊，避免头部垄断分数。

---

### Q6 · "归一化"是什么？项目里的三处化身

一句话：**把不同量纲/范围的数值映射到统一尺度，才能公平地比较、加权或合并**。（像 Java 里不该把"响应时间 ms"和"内存 KB"直接相加当综合指标）

| 方法 | 公式 | 项目应用 |
|---|---|---|
| 长度归一化 | `b·\|D\|/avgdl` | BM25 长短文档公平比较（Q3） |
| L2 归一化 | `v/‖v‖` | embedding 向量单位化后内积=余弦相似度 |
| 排名融合 | `1/(k+rank)` | RRF 把异构分数统一成"排名分"再安全累加（Q5） |

口语中"归一化"（压到固定区间如 [0,1]）与"标准化"（均值0方差1）常混用；面试时能一句带过二者的区分，即是加分点。

## 三、重排专题

### Q7 · RRF 融合排序 vs LLM 重排——都叫"排序"，性质完全不同

先给结论：① 是零成本的数学归并，② 是真读内容的语义精排。代码位置（`retrieve()` 尾部的融合排序与可选重排两行）：

```python
fused_list = sorted(fused.values(), key=lambda c: c.score, reverse=True)   # ① RRF 融合排序
...
if ...ENABLE_RE_RANK...:
    fused_list = await self._llm_rerank(query, fused_list, k)              # ② LLM 重排
```

| 维度 | ① RRF 融合排序 | ② LLM 重排 |
|---|---|---|
| 依据 | 数学公式，只看"你在每路排第几名" | 模型**读内容**判断语义相关性 |
| 理解能力 | 零 | 真·语义理解 |
| 成本 | 微秒级、免费、确定性强 | 每条候选拖一次 LLM API，慢且花钱 |

**为什么有了①还需要②**：RRF 只继承两路的排名，**不能发现两路的共同错误**。"某 chunk 提到'华信科技'20 次 → BM25 登顶 + Dense 沾边也靠前 → RRF 之后它照样登顶"——但它实际是公司简介而非营收数字，只有读过内容的重排能把它压下去。本质是**词面相关 ≠ 语义相关**。

Java 类比：①≈多数据源结果按规则 merge 归并；②≈领域专家逐条人工复审——贵但准。工业界流水线漏斗形：**召回（求全）→ RRF（免费合并）→ 重排（求准，只喂 top-N）→ 截断**，越往后候选越少、单条越贵。

**项目实测结论（可直接引用）**：小语料下重排是负优化——几百个 chunk 里 Dense+BM25+RRF 已足够准，LLM 波动和延迟超过纠错收益，故默认 `ENABLE_RE_RANK=false`（README 第六节）。又一个"知道什么时候不用某技术"的决策案例。负优化的完整量化机制拆解见 Q8。

关联 → Q8（负优化量化复盘）、Q9（cross-encoder 精排正解）

### Q8 · LLM 重排为什么实测是负优化？（量化复盘）

#### 问题现场

`_llm_rerank` 已上线，直觉是"精排总比不排好"，但 golden set 三路对比全面降分（数据见 [评估体系.md](评估体系.md) Q0）：文档 Hit@1 94.3%→88.6%，答案 Hit@3 100%→94.3%（2 条含答案 chunk 被挤出前排），且每条 query 多付一次 LLM 调用。

#### 先厘清一个误区

**重排不减少召回**（候选池不变），伤害的是 Top-k 内的相关占比——即精确率。机制一句话：**排对了加分，排错了把相关 chunk 挤出 Top-k、把无关的换进来**。

#### 四个机制

1. **输入截断**：重排 prompt 只给 LLM 看每个 chunk 前 120 字符，而 chunk 有 500 字符——答案在后半段的 chunk 被"看开头就误杀"；
2. **基线饱和**：小语料（36 块、候选 8 块）下 RRF 已达答案 Hit@3=100%，重排没有上行空间、只剩犯错空间；
3. **高方差**：temperature 随机性 + 一次排 8 个候选的位置偏差与注意力稀释；对比 RRF 是零方差纯数学、完全可复现；
4. **增益/代价比倒挂**：LLM 打分或许低偏差（真读内容），但基线已最优时，方差代价远大于偏差收益。

#### 出路与决策

换**判别式**精排模型（cross-encoder / BGE-Reranker，见 Q9），或只对低置信度区间精排；小语料默认关重排（`ENABLE_RE_RANK=false`），语料扩大后用 golden set 复测回正再开。

**面试话术**："我实测证明重排在候选池小、基线已饱和时是负优化：重排不减少召回，只会把相关 chunk 挤出 Top-k——输入截断 120 字符加上 LLM 打分的高方差，误差全是净损失。所以默认关重排，语料扩大复测回正再开，或者直接换 cross-encoder。"

关联 → Q7（RRF vs 重排定性对比）、Q9（cross-encoder 正解）、[评估体系.md](评估体系.md) Q0（实测数据）

### Q9 · Bi-Encoder vs Cross-Encoder：为什么重排不能替代召回

#### 架构对比

| | Bi-Encoder 双塔（召回） | Cross-Encoder 交叉（精排） |
|---|---|---|
| 输入 | query 和文档分开编码，各得一向量 | `[CLS] query [SEP] 文档` 过同一模型 |
| 打分 | 余弦相似度 | 注意力让 query 词与文档词逐词交互后直接输出相关性分 |
| 速度 | 快：文档向量离线预计算，在线 ANN 毫秒级搜全库 | 慢：每对 (query, doc) 都要完整前向，无法预计算 |
| 精度 | 一般：各自压成单向量，细节丢失 | 高：捕捉"看着像但不相关"的细粒度差异 |
| 用途 | 全库召回（Dense 路） | 小候选集精排（重排） |

**BGE-Reranker** = 智源（BAAI）开源的 cross-encoder 重排系列（bge-reranker-v2-m3 等），中文强、可本地部署，RAG 精排的事实标准。**cross-encoder 是架构，BGE-Reranker 是具体模型。**

#### 为什么重排不能替代召回

cross-encoder 无法预计算 → 只能在线逐对打分 → 全库逐对算会卡死 → 工业界永远是"Bi-Encoder + BM25 宽召回几十条 → cross-encoder 对这几十条精排"。

#### 对照 `_llm_rerank` 三个毛病，cross-encoder 天然没有

| 项目实测问题 | cross-encoder |
|---|---|
| 截断 120 字符判断依据残缺 | 整块进 512 token 窗口全文打分 |
| temperature 随机 + 位置偏差（8 个一起排） | 判别式纯分数输出，零随机、逐对独立无位置干扰 |
| 每条一次 LLM 调用贵且慢 | 单次前向毫秒级，本地可跑零 API 费 |

**接入方式**：`_llm_rerank` 替换为 `sentence_transformers.CrossEncoder("BAAI/bge-reranker-v2-m3").predict([(query, c.text) ...])`，接口形态一致（进候选出排序），主链路不动。**落地后必须复测 golden set**，验证能否把重排从负优化扭成正优化（Q8）。

## 四、分块与检索纠错

### Q10 · 分块策略三层递进：overlap → 语义分块 → 父子分块

#### 问题现场

三个连环追问：`CHUNK_SIZE=500 / CHUNK_OVERLAP=50` 怎么来的？语义分块切出超大块怎么办？父子分块下构建上下文到底用子块还是父块？

#### 第一层：固定分块 + overlap（当前方案）

切下一块时回头带上前一块末尾 50 字符（约为 chunk_size 的 10%~20%，经验区间），防止句子正好跨在切割点被劈成两半。代价有二：索引膨胀（重复存储）；同一内容多块命中——后者由 RRF 以 `page_content` 为 key 天然去重（融合循环里的 `fused.setdefault`）。

#### 第二层：语义分块的常见误解

- 语义分块找的是**断点**不是"凑大小"：句间相似度骤降处下刀，**块大小是切完的结果，不是输入目标**；
- 全文主题连贯（如估值方法论一文）会一路不切产出超大块 → 实际实现必须带 `max_chunk_size` 硬上限兜底（语义优先、尺寸兜底）；
- 更本质：**块大了 embedding 本身失效**——整块压成一个向量，多主题混杂使向量"平均化"，与 query 比相似度哪边都不突出，召回率反崩。**靠加大块换完整性是死路**。

#### 第三层：父子分块——检索单元与返回单元分离

| 角色 | 用途 | 粒度 |
|---|---|---|
| 子块 child | 做 embedding、参与检索匹配 | 小（~200 字），向量干净、检索准 |
| 父块 parent | 命中后返回给 LLM 的上下文 | 大（~1500 字），语义完整 |

**子块负责"找到"，父块负责"讲清"。** 三个工程细节：①父块去重（多子块命中同一父块按 parent_id 合并，不浪费上下文名额）；②父块排序（按其名下最高分子块分）；③预算控制（父块变大后做总 token 预算，必要时截断或摘要）。

**落地方式与验证**：`retrieve()` 返回子块用于打分溯源，`retrieve_node` 改为把父块文本写入 state；预期收敛答案级与文档级之间约 3pp 的假阳性落差——以 `compare.py --skip-rerank` 复测前后答案 Hit@1 差值验证。

**面试话术**："分块我用固定 500 字符加 50 overlap 防句子被切点劈开；语义分块我理解它找的是断点不是大小，必须配 max_chunk_size 兜底，而且块大了向量被多主题稀释反而伤召回——所以终极方案是父子分块：子块当探头保证检索准，父块保证上下文完整，检索单元和返回单元分离。"

### Q11 · 检索纠错：CRAG / Self-RAG，置信度 ≠ 答案可信度

#### 问题现场

检索结果不可靠时硬生成还是先纠错？CRAG 的置信度是不是"答案可信度"？落地要不要在工作流上加节点？

#### 两个框架的分工

**CRAG（Corrective RAG）**——外部评估器把关检索质量，不行就换来源：

```
query ──→ 检索 ──→ 相关性评估器打分
                      │
        ┌─────────────┼──────────────┐
     Correct       Ambiguous      Incorrect
        │             │              │
    知识精炼       混合两路      触发网络搜索兜底
        └─────────────┴──────────────┘
                      ▼
                   再生成答案
```

**Self-RAG**——让 LLM 自己发射"反思 token"边生成边自省：`Retrieve?`（按需检索）、`ISREL`（文档相关吗）、`ISSUP`（答案被文档支持吗，即忠实度）、`ISUSE`（有用吗）。需微调模型才能发射反思 token，落地成本高于 CRAG。

#### 置信度分层（关键澄清）

CRAG 的置信度属于**检索层**——判断"找来的材料靠不靠谱"，此时答案还没写；"答案可信吗"是生成层的忠实度（faithfulness，见 [评估体系.md](评估体系.md) Q2）。两层别混：

| 层 | 测什么 | 时机 | 代表 |
|---|---|---|---|
| 检索层置信度 | 检回文档与 query 多相关 | 生成**前**的门禁 | CRAG evaluator |
| 生成层可信度 | 答案是否被上下文支持 | 生成**中/后**自查 | Self-RAG ISSUP、RAGAS |

本项目 README 检索排查思路中"融合分数低于阈值 → 扩召回 + 二次检索"即 CRAG 思想的零训练简化版：RRF 融合分天然可做检索层置信度代理指标。

#### 工作流落地两档（评估器不一定是"别的模型"）

评估器三形态（由轻到重）：**规则/分数**（RRF 融合分阈值，零成本）→ **轻量模型**（BGE-Reranker 类 cross-encoder 打分，毫秒级）→ **LLM-as-judge**（逐 chunk yes/no，LangGraph 官方示例做法）。教训迁移：LLM 重排已实测负优化（Q8），**评估器选型同样必须过 golden set 验证**。

- 方案 A（最小侵入）：`retrieve_node` 内部查分、低分在函数里二次检索。图不变，但纠错黑箱化、不可观测；
- 方案 B（标准 CRAG 图，**本项目决策**）：

```
START → retrieve → grade ──(correct)──→ agent ⇄ tools → generate
                      │
                      └──(incorrect)──→ rewrite_query ──→ retrieve（回环）
```

新增 `grade`（逐 chunk 相关性标记）与 `rewrite_query` 两节点 + 条件边回环，各挂 `@trace` 可观测；**必须带重试上限**（如最多纠错 2 次）防死循环烧钱——与 ReAct 回环上限控制同源（见 [Agent架构.md](Agent架构.md)）。选 B 还因它展示"条件边路由 + 回环 + 上限"的手写图能力。

**面试话术**："检索纠错我用零训练版 CRAG 的思路：RRF 融合分做检索层置信度门禁，低于阈值就改写 query 重检一次，带上限防死循环。注意 CRAG 的置信度是检索层的，判断的是材料靠不靠谱；答案可不可信是生成层忠实度的事，两层别混。"

## 五、向量库选型

### Q12 · 不同向量数据库的主要差异维度

直觉里"规模 + 检索质量"两个维度对了一半，完整的正交维度有三个：

**① 索引算法（决定规模上限与速度）**

| 索引 | 原理 | 特点 |
|---|---|---|
| Flat 暴力扫 | 全量算距离 | 100% 精确，万级以下无所谓 |
| HNSW 图 | 多层跳表式近邻图 | 主流默认，快且准，吃内存 |
| IVF+PQ | 聚类分桶+向量压缩 | 十亿级方案，牺牲精度换内存 |
| DiskANN | 磁盘索引 | 内存装不下时 |

**② 过滤实现（真正拉开"检索质量"差距的地方）**

各家召回率都能调高（HNSW 拉 `ef_search` 即可），差距在元数据过滤：`WHERE dept="财务" AND year=2024` + 向量搜索，是 pre-filter（先滤再搜）还是 post-filter（先搜后丢）？post-filter 在过滤命中稀少时会"滤空"。Qdrant 以 pre-filter 实现著称。

**③ 部署形态与运维**

| 产品 | 定位 | Java 心智类比 |
|---|---|---|
| FAISS | Meta 的索引**库**，非数据库（无服务化/持久化管理） | 一个 JAR 包 |
| Chroma（本项目） | 嵌入式轻量，原型/教学 | SQLite / H2 |
| pgvector | 复用现有 PostgreSQL，千万级内很能打 | 主库加个表 |
| Qdrant | Rust 单二进制，过滤强 | 单机 MySQL++ |
| Milvus | 分布式，十亿级 | 分库分表的 MySQL 集群 |
| Pinecone | 全托管免运维 | 云厂商 RDS |

**选型四问框架**（比背产品表更加分）：数据量级？→ 要强元数据过滤吗（多租户刚需就别选 post-filter 实现）？→ 已有基础设施吗（已有 PG 则 pgvector 几乎白送）？→ 谁来运维？

**本项目 Chroma 选型逻辑**：与 rank_bm25 同款 YAGNI——教学语料几百 chunk、嵌入式零部署、LangChain vectorstore 抽象接口统一，迁移成本可控。边界：千万级迁 Qdrant/pgvector。

## 演进路线（检索增强实验清单，每项过 golden set 验证）

本质是消灭假阴性（召回）或假阳性（精度），按"问题出在哪一层"对症下药：

| 层 | 问题 | 方法 |
|---|---|---|
| 查询层 | query 与文档表述差异大 | Multi-Query 多路改写合并去重；HyDE（先生成假设答案再用它检索）；查询扩展/缩写展开 |
| 分块层 | 答案被切碎 | 加大 overlap；父子分块（Q10）；语义分块 |
| 检索层 | 单路召回有盲区 | 多路召回（已有）；放宽 candidate_k 先宽进后精排；降低相似度阈值 |
| 流程层 | 一次检索不够 | CRAG 纠错重检（Q11）；元数据路由缩小搜索域 |

**性价比排序**：① Multi-Query 改写（改动小，对 semantic/fuzzy 用例收益最大）→ ② 父子分块（针对答案级比文档级低的 3pp 假阳性）→ ③ CRAG 二次检索（方案 B 图）→ ④ BGE-Reranker 替换 `_llm_rerank` 后复测。

所有手段都增加延迟/成本——先跑 `eval/compare.py --skip-rerank` 留基线，改完复测，指标上升才合入。
