# 概念与术语 —— 检索评估词汇表

> 本表汇总 `eval/` 检索评估体系中用到的概念与术语，全部用中文解释，
> 并标注项目锚点（代码 / 文档位置）。数据示例均来自本项目实测（35 条 golden set，Top-5）。
> 配套详解见 `docs/思考与方案/`（评估体系.md Q0、RAG与检索.md Q7–Q12）。

---

## 一、核心指标

### Hit@k（命中率）

**中文**：前 k 命中率 / 召中率。

**解释**：对每条查询，只看检索返回的前 k 个结果——里面出现了期望的来源就算命中（记 1），否则记 0；所有查询取平均。

- `Hit@1`：排第 1 的必须命中 → 最严格，衡量**排序**质量
- `Hit@3`：前 3 内命中即可 → 衡量**召回**质量

**示例**：35 条里 dense 的 Hit@1 = 91.4%，即 32 条的第 1 名检索结果都对了，3 条排错。

**项目锚点**：`eval/metrics.py` 的 `hit_at_k()`。

### MRR（Mean Reciprocal Rank，平均倒数排名）

**中文**：平均倒数排名。不问"命中没有"，而问"**命中在第几名**"。

**解释**：对每条查询，找到期望来源首次出现的排名 rank，得分为 `1/rank`（第 1 名得 1.0，第 2 名得 0.5，第 3 名得 0.33……没进前 k 记 0），全部取平均。比 Hit@k 更"惜名次"——差一名就差一半分。

**示例**：某条查询期望文档排在第 2 名 → 该条 MRR 贡献 0.5。

**项目锚点**：`eval/metrics.py` 的 `mrr_at_k()`。

### 文档级 / 答案级（本项目自定义的双口径）

**中文**：两套命中判定标准。

| 口径 | 判定问题 | 严格程度 |
|---|---|---|
| **文档级**（hit@k / mrr@k） | Top-k 里是否出现期望**来源文档** | 宽松：命中该文档任意 chunk 即算 |
| **答案级**（ans_hit@k / ans_mrr@k） | 期望**答案片段**是否真实出现在召回 chunk 文本里 | 严格：文档对了但 chunk 里没答案仍算失败 |

**为什么要有两套**：文档级存在假阳性（详见下文），答案级更贴近"LLM 拿到的上下文里到底有没有答案"。实测两者差距约 3pp。

**项目锚点**：`metrics.py` 的 `answer_hit_at_k()` / `answer_mrr_at_k()`；`golden_set.yaml` 的 `answer` 字段。

## 二、打分基准

### Golden set（黄金集 / 金标准集）

**中文**：人工标注的标准测试集。

**解释**：一组"问题 + 标准答案"的用例集合，用作系统打分的固定考卷。每次改代码、换策略后重考一遍，分数对比即知好坏——优化的"依据"、回归的"门禁"。

**项目锚点**：`eval/golden_set.yaml`（35 条，含 direct/semantic/fuzzy 三类难度）。

### Ground truth（金标准 / 真值）

**中文**：客观上正确的事实，打分时的对照基准。源自测绘学"地面基准控制点"。

**解释**：golden set 里每条标注的 `expected_sources` 和 `answer` 就是 ground truth——不管系统怎么检索，最终都要回到这个真值来对账。

**关系**：golden set ≈ ground truth 的集合，这就是"黄金集"名字的由来。

## 三、混淆矩阵家族（命中与错误怎么分类）

### 四象限：TP / FP / FN / TN

以"每个候选 chunk **该不该被召回**"为判定对象：

| | 系统召回了 | 系统排除了 |
|---|---|---|
| **实际相关** | 真阳性 TP ✅ 找对了 | 假阴性 FN ❌ 漏了 |
| **实际无关** | 假阳性 FP ❌ 掺了 | 真阴性 TN ✅ 排对了 |

### 假阳性（False Positive, FP）

**中文**：误报。系统说"命中"，实际没对——表面 ✓ 实际 ✗。

**RAG 场景**：目标文档进了 Top-k，但召回的是该文档的**无关 chunk**，答案根本不在里面。危害：文档级指标虚高，掩盖"上下文里没答案"的隐性失败，LLM 照样编造。答案级判定专门抓它。

### 假阴性（False Negative, FN）

**中文**：漏报。答案所在 chunk 该找到却没找到（没进 Top-k）。

**危害**：比假阳性更致命——假阳性只是浪费 token，假阴性让 LLM 无据可依、直接幻觉。

### Precision（精确率）

**中文**：精确率 / 查准率。公式 `TP/(TP+FP)`。

**口诀**：分母是**你返回的东西**——返回的 8 条里有 6 条相关 → 6/8 = 75%。衡量"报上来的干不干净"。

### Recall（召回率）

**中文**：召回率 / 查全率。公式 `TP/(TP+FN)`。

**口诀**：分母是**客观存在的相关总量**——共 10 条相关找回 6 条 → 6/10 = 60%。衡量"该找的漏了多少"。

**对比记忆**：**P 看"返回的里面"，R 看"全部相关里面"**。两者此消彼长，工程上靠 Top-k、阈值、重排调平衡。

## 四、检索策略术语

| 术语 | 中文 | 一句话解释 | 项目锚点 |
|---|---|---|---|
| Dense | 稠密/向量检索 | query 与文档各编码成向量比相似度，兜"意思近字面不同" | `retrieve_dense()` |
| Sparse / BM25 | 稀疏/关键词检索 | 词频统计打分，兜"罕见词精确命中" | `_tokenize` + `BM25Okapi` |
| hybrid | 混合检索 | Dense + BM25 两路召回合并，互补盲区 | `retrieve()` |
| RRF | 倒数排名融合 | 只看排名不看分数：`score=Σ 1/(60+rank)`，零方差可复现 | `retrieve()` 内 |
| rerank | 重排/精排 | 对召回候选二次排序；LLM 版已实测为负优化（小语料） | `_llm_rerank` |
| Cross-Encoder | 交叉编码器 | query+文档拼接过同一模型逐词交互打分，准但慢，只适合小候选集精排 | —（升级位） |
| Top-k | 前 k 个结果 | 最终返回给 LLM 的上下文块数 | `RETRIEVAL_TOP_K` |
| candidate_k | 候选宽度 | 多路召回时先多取（宽进），融合/精排后再收窄 | `candidate_k = max(k*2, k+4)` |
| chunk | 分块 | 文档切出的检索单元（本项目 500 字符，overlap 50） | `rag_retriever.py` |

## 五、生成层评估术语（对照）

| 术语 | 中文 | 一句话解释 |
|---|---|---|
| Faithfulness | 忠实度 | 生成答案是否被检索上下文支持——"说的话都有出处吗"，直接对抗幻觉。与检索评估方向相反：前者拿**模型的话对证据**，后者拿**系统输出对标准答案** |
| LLM-as-judge | 模型当裁判 | 用（另一个）LLM 按评分标准给输出打分，如 faithfulness 的原子断言校验 |
| Hallucination | 幻觉 | 模型生成上下文中不存在的信息。假阴性（没检到）是幻觉的主要诱因之一 |
| 置信度（检索层） | 检索质量置信度 | CRAG 语境：评估器对"检回材料与 query 相关度"的打分，生成**前**的门禁，**不是**答案可信度（见 `docs/思考与方案/RAG与检索.md` Q11） |

---

## 六、一句话串起全部指标

> 拿 **golden set**（考卷）上的 **ground truth**（标准答案）对照检索结果：
> **Hit@k** 问"找没找到"，**MRR** 问"排在第几"，**答案级口径**抓"文档对了但没答案"的**假阳性**；
> **Precision/Recall** 分别管"准"和"全"；检完之后 **faithfulness** 再管"说的有没有出处"。
